# 06 · 如何知道一個 Mod 值得導入

[回首頁](../README.md) · 2026-10-05 · **本章是實驗設計；沒有尚未取得的 benchmark 結果。**

## 比較對象應是最小可用方案，不是「什麼都不用」

建議三組：

- **A：原生基線。** 固定 Claude Code 版本、模型、effort、repo commit、提示與基本設定。
- **B：較窄擴充。** 依需求加入 statusline、skill、settings hook 或 MCP；用最少能力解決同一件事。
- **C：Mod。** 保持其他條件一致，只加入待測 Mod；記錄版本和所有其他 installed／built-in 元件。

只比較 A 與 C，容易把「有任何輔助」的改善，誤認成「必須使用 Mods」的價值。模型路由、記憶系統和多代理框架另有大量變數，不能跟一個 UI Mod 混在同一場排名。

## 先定驗收，再開始測

| 面向 | 建議量測 | 常見錯誤解讀 |
| --- | --- | --- |
| 任務品質 | 獨立測試通過、人工重工分鐘、遺漏缺陷 | agent 說完成就算成功 |
| 人工負擔 | 審查／找資料／確認操作的有效分鐘 | 把模型等待都算成可回收工時 |
| 時間 | 端到端時間、hook 額外延遲、冷啟動 | 只報最快一次 |
| 模型成本 | input/output、cache read/write、額外 model calls | 把 token 減少直接當現金省下 |
| 操作風險 | 誤報、漏報、拒絕後副作用、資料外流 | 攔下一例就宣稱安全 |
| 維護 | 更新所花工時、故障／停用次數、相容性 | 忽略 Claude Code 升級 |
| 採用 | 被啟用的頻率、實際互動、停用原因 | stars、下載量等於留存或付費意願 |

Token／快取成本機制參考[成本文件](https://code.claude.com/docs/en/costs)、[prompt caching](https://code.claude.com/docs/en/prompt-caching)、[Mods 模型呼叫](https://code.claude.com/docs/en/plugins/mods/api#call-a-model)。`$.model.complete`／`fork` 會消耗 session 方案或 API key；沒有模型呼叫的 Mod 也可能增加 CPU、I/O 或開發維護成本。

## 可重跑的 pilot

1. 選一個痛點，例如「Reviewer 不知道 CI 結果是否屬於目前 commit」，不要以泛稱「提高生產力」為目標。
2. 準備可復原的 repo fixtures 和事先寫好的驗收；用合成資料，不帶生產 secrets。
3. 在相同起始狀態跑 A／B／C，交錯順序，重複測試以觀察波動；設定樣本數與停損，不跑到看到想要的數字才停。
4. 分開記錄 warm／cold cache、人工點擊、模型等待、工具執行和 retry；不要把快取與學習效應混成 Mod 效果。
5. 由不知道組別的 reviewer 按同一標準驗收，保存去識別化結果；所有失敗也要留下。
6. 同時報告個別資料、成功比例、典型時間與變異；小樣本不宣稱統計顯著或普遍適用。
7. 如果較窄的 B 已達標，就停止增加功能；如果 C 只省幾秒卻新增外洩面，優先不導入。

這是建議流程，不表示本研究已執行 A/B/C 實驗。UI Mod 另要測窄／寬 terminal、Desktop、無 UI surface 及多 Mod 競爭。

## 月度價值模型

用同一貨幣和月份估算：

\[
V = \frac{N\,t}{60}H - \frac{C_{build}}{M} - C_{maint} - C_{usage} - C_{risk}
\]

- \(N\)：每月有效使用次數；\(t\)：每次實測省下的人工分鐘；\(H\)：每小時人工成本。
- \(C_{build}\)：一次性開發／評估成本；\(M\)：攤提月數。
- \(C_{maint}\)：月維護成本；\(C_{usage}\)：額外模型／基礎設施支出。
- \(C_{risk}\)：新增風險的月期望損失；不能估就做情境分析，不要默默當零。

**純假設算例，非實測：**每月使用 300 次，每次省 2 分鐘，每小時 NT$1,000，等值人工時間為 NT$10,000。建置 NT$12,000 分 6 個月攤提＝NT$2,000；月維護 3 小時＝NT$3,000；額外用量 NT$1,000；在尚未計風險前，月淨值為 NT$4,000。

這不是新增營收，也不一定是可裁減的現金成本。訂閱方案內 token 減少可能只是多出配額；如果品質下降、需要重工或過度信任 UI，淨值可能轉負。

## 先用三個實驗取代排行榜

### 實驗 A：statusline vs context Mod

相同長任務，比較使用者察覺壓力、主動整理 context 的時點與最後品質。刻意加入 usage 讀取失敗及快要 compact 的邊界，驗證 UI 不把過期數據當現況。

### 實驗 B：內建 diff vs edit replay

讓獨立 reviewer 找同一 patch 的缺陷；混入失敗 Edit、後續覆寫和 Bash 修改。驗證 replay 是否幫理解，而非多一個漂亮但不準確的時間軸。

### 實驗 C：文字確認 vs 影響預覽

在無真實副作用的測試替身中，混合 benign／risky、wrapper、compound command、未知解析與目標改變。計算誤報、漏報和人工確認時間；不在正式環境實際刪資料來驗證。

## 現階段建議

個人先從觀察型工具開始；團隊優先找一個反覆出現的 CI／review 摩擦；企業先做來源、能力與資料治理。沒有資料支持的收益就保留為假設，讓下一位研究者能重跑、反駁與修正。
